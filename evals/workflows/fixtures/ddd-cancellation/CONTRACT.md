# Cancellation and refund contract
Public API (preserve function names and signatures):
- ordering.cancel(order) returns a new order dict. Order has id and status (open/cancelled/shipped), plus optional metadata. Open becomes cancelled; cancelled is idempotent. Shipped raises ValueError without invoking billing. Other fields survive.
- billing.refund(payment, send_refund) returns a new payment dict. Payment has captured and refunded integer cents (0 <= refunded <= captured) and refund_state (none/failed/refunded), plus optional metadata. Reject invalid amounts (including bool) with ValueError before a provider call. Request exactly captured-refunded cents. A positive request calls send_refund(amount) once. Normal return means success: refunded becomes captured and refund_state becomes refunded. RuntimeError means provider failure: refunded stays unchanged, refund_state becomes failed. Other exceptions propagate. Nothing outstanding means no provider call and refund_state refunded.
- checkout.cancel_order(order, payment, send_refund) returns (updated_order, updated_payment). First apply ordering policy; then request a refund via billing. Provider RuntimeError does not undo a valid cancellation. Retrying a cancelled order retries only the outstanding refund. A successful retry must not refund twice.
All functions leave input records and nested metadata unchanged; returned top-level records are independent. Do not invent a transaction that claims the external provider can be rolled back. No concurrency or durable retry guarantees are required here.
Ordering owns order state, Billing owns money/refund state, checkout coordinates. Business decisions must be callable without HTTP, storage or a running service. Existing records are plain dicts; retain this API. No extra dependencies, services or database are needed. Tests may use stdlib unittest. Existing docs may be corrected if necessary, not duplicated.
